# Go-live: what we prove on the real server before the first client

Both products run on one Ubuntu 24.04 server (AWS Lightsail first; Contabo or Hetzner work the same):
Jarda from this repo ([deploy/vps/README.md](../deploy/vps/README.md)), FlowLine from its own repo
(FlowLine `docs/DEPLOY-VPS.md`, whose section 5 is FlowLine's cutover checklist). Every scenario below is
run on that server, by an engineer with SSH, before any client gets a link. Each one ends with a line in
the **Results** table and its output under [docs/evidence/go-live/](evidence/go-live/).

`K=/opt/jarda/deploy/vps/scripts` in the commands below. Run them as root (`sudo -i`).

## The scenarios

| #   | Scenario                                                     | How to prove it                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Passes when                                                                                                                                                    |
| --- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | DNS + HTTPS for every subdomain                              | `$K/go-live-check.sh flowline.<domain>`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | `DNS`, `redirects to HTTPS` and `HTTPS … trusted certificate` PASS for jarda, jarda-api and flowline; result `ALL PASS`                                        |
| 2   | First owner sign-up                                          | Browser: `https://jarda.<domain>/ar/register`, create the owner account and the organization, sign out, sign in again                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | The dashboard opens after sign-in; the account is in the database (`$K/compose.sh exec -T postgres psql -U jarda -d jarda -Atc 'select count(*) from "User"'`) |
| 3   | Email delivery, or a clear message without it                | **Email set up** (README section 5): `$K/alert.sh "test"` arrives, and "Forgot password" sends a reset email. **Not set up:** "Forgot password" shows "No email arriving? Ask your organization owner…", the owner creates a one-time link in Settings → Team & Roles, and sending an invoice by email says "Email is not configured"                                                                                                                                                                                                                                                                          | Either the email arrives, or every screen that would send one says so plainly and offers the way round                                                         |
| 4   | Server reboot: everything comes back by itself               | `reboot`; after about 3 minutes `uptime` and `$K/go-live-check.sh flowline.<domain>`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Uptime shows the reboot; `ALL PASS`; the owner from scenario 2 can still sign in; FlowLine health is green                                                     |
| 5   | App crash: it restarts by itself                             | `docker inspect -f '{{.RestartCount}}' $($K/compose.sh ps -q api)`, then `kill -9 $(docker inspect -f '{{.State.Pid}}' $($K/compose.sh ps -q api))`; repeat for `web`. Watch `curl -fsS https://jarda-api.<domain>/api/health` (api) and `curl -fsS https://jarda.<domain>/robots.txt` (web)                                                                                                                                                                                                                                                                                                                   | Within about a minute the restart count is one higher and the matching address answers again, with no one touching the server                                  |
| 6   | Backup runs, restore into a scratch database                 | `systemctl start jarda-backup.service; cat /srv/jarda/backups/backup.status`, then `$K/restore.sh --check`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | `OK …` in the status file; `restore-check OK … originals=verified scratch=dropped` (the live database is not touched)                                          |
| 7   | Full restore of the live data (only before the first client) | `$K/restore.sh --list`, then `$K/restore.sh --snapshot <id> --yes`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | `restore OK`; the data is exactly the snapshot's (counts and ledger checked by the script)                                                                     |
| 8   | Roll back to the previous version in under 5 minutes         | Needs two versions on the server: run `install.sh` again after a newer commit (the server keeps the running one and the one before). Then `$K/rollback.sh --list`, `time $K/rollback.sh`, and back again with `$K/rollback.sh --to <newer>`                                                                                                                                                                                                                                                                                                                                                                    | `rollback OK … seconds=N` with N under 300, health green, the owner can sign in                                                                                |
| 9   | Disk / memory alert                                          | Every 5 minutes the health check alerts on disk above 80%, less than 300 MB of free memory, an app container down, a failed or missing backup, or an HTTPS certificate with less than 14 days left. Prove the path: `fallocate -l <size> /srv/jarda/alert-test.fill` (instant, writes nothing) to push the disk above 80%, `systemctl start jarda-healthcheck.service`, `journalctl -t jarda-alert -n 5`; then `rm /srv/jarda/alert-test.fill` and run the check again                                                                                                                                         | An `ALERT: disk …% used` line, and later `RECOVERED: disk`; by email too when email is set up (scenario 3), on Telegram when its two settings are set          |
| 10  | HTTPS certificates renew by themselves                       | Caddy renews about 30 days before expiry and the health check alerts at 14 days left. Prove issuing works unattended: note the serial (`echo \| openssl s_client -connect jarda.<domain>:443 -servername jarda.<domain> 2>/dev/null \| openssl x509 -noout -serial -enddate`), remove that host's stored certificate (`rm -r /srv/jarda/caddy/data/caddy/certificates/*/jarda.<domain>`), `$K/compose.sh restart caddy`, wait a minute, read the serial again                                                                                                                                                  | A new serial and a fresh end date, no manual step. Do this once only (Let's Encrypt allows 5 identical certificates a week)                                    |
| 11  | Happy-path browser suite against production                  | From a developer machine. Jarda ([E2E-BROWSER.md](E2E-BROWSER.md), tags and base address from PR #660): `E2E_BASE_URL=https://jarda.<domain> E2E_API_URL=https://jarda-api.<domain>/api pnpm e2e:happy`; it registers organizations named "QA Production Check …" with `*@example.test` addresses, so take a backup first (`systemctl start jarda-backup.service`) and restore it afterwards (scenario 7). FlowLine (its `docs/E2E.md`): `bun install && bunx playwright install chromium && E2E_BASE_URL=https://flowline.<domain> bunx playwright test` runs its `@happy` journeys, which create no accounts | Every `@happy` test passes; the result (count, time, commit) is recorded                                                                                       |

Order on the day: 1, 2, 3, 6, 9, 10, 5, 4, 8, then 11 followed by 7 (that restore also removes the test accounts).

## If a scenario fails

Stop and fix it before any client gets the link. Re-run the scenario and then `go-live-check.sh`. Never
share the address while a line in the table is not PASS.
