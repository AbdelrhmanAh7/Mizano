## First-client proposition and scope

Serve **one Egyptian small service business**, EGP books, an authorized owner and an accountant, initially with cash/bank payments recorded manually or from a statement. This is an explicit planning assumption, not observed customer demand. Validate the business type, taxpayer obligations, document volumes, opening balances, support expectations and willingness to pay with the actual client before promising scope. Record those answers in a private onboarding record, never in public fixtures.

The practical offer is: set up in Arabic, record a quote and invoice, collect partial/final payments, record bills/expenses, import documents into a reviewed draft, and close a reconciled month with recoverable originals. Preserve the repository's [Pi goal](../roadmap.md) and [acceptance contract](../strategy/demo-acceptance.md): CPU intake, Telegram, exceptions, explicit batch approval and an actual Raspberry Pi 5 deployment remain gates. No new HR/CRM/manufacturing/POS scope. Do not touch Hetzner, production secrets or live databases in these development sessions.

**Choose the statutory issuer before onboarding real sales.** For ETA-obligated transactions, either use a validated Mizano adapter or retain the client's existing authorized issuer and reconcile its document IDs/statuses to Mizano's books. A bookkeeping-only pilot must say who issues and handles rejection/returns. “Not compliant yet” is disclosure, not permission to issue a noncompliant invoice. A client needing Mizano as its sole statutory issuer is blocked until that adapter passes its gates. See [country requirements and official sources](../research/competitors.md#what-an-egyptian-or-saudi-client-legally-needs); Saudi and UAE issuance are later expansions.

Stop feature expansion once this first client and the owner's assigned dependencies meet the checklist. Do not chase competitors' total feature counts. Price, acquisition cost, demand and retention are unknown; this plan invents none of them.

Browser batches every **10 seconds or 20 events** to the product's own server, bounds payload/queue length, drops nonessential queued events on opt-out, and uses event UUIDs to dedupe replay. The shared design calls for `navigator.sendBeacon` on page hide. **Implementation constraint for A3/W10:** Beacon cannot set custom auth or the UI's `Accept-Language` header. Use authenticated same-origin BFF/session transport and a locale-preserving `fetch(..., { keepalive: true })` hide flush wherever needed to satisfy the newer “every request uses UI language” rule; do not put tokens in body/URL or silently weaken that rule to force Beacon. The coordinator records the final transport decision with the locale owner. Ordinary batching also sends `Accept-Language`.

The server validates the registry/version and payload bound, obtains the current authenticated user and organization itself, enforces membership, rate limits per user/org, and writes `product_events` in Postgres indexed by `(organizationId, occurredAt)`. Unique event IDs are scoped to the authenticated org; client IDs never grant tenancy. Keep client occurrence time bounded and authoritative received time for ordering. Store no complete browser URL or user-agent fingerprint. Server command-success events are authoritative; client clicks cannot forge posted/payment funnel completion.

Add **per-user opt-out** in settings. Only defined essential operational audit/security events continue; analytics, ranking history and recommendation interaction telemetry stop. Existing audit logs remain separate and obey accounting/security retention. Scheduled deletion removes product events older than **180 days**, in bounded batches with observable failure/retry. Admin views require an explicit permission and only aggregate that org; no global client ranking or cross-tenant raw event access.

Admin first-client funnel: eligible signups → setup complete → first draft → first posted result → first receipt → first month review. Show org/user denominators, time window, event definition/version, incomplete periods and zero-data state. For one client prefer counts and elapsed time; do not imply meaningful conversion-rate improvements or causal attribution from a tiny sample. The event naming/retention policy is implementation acceptance, not a demand estimate.

## Recommendations that help finish work

Start with **rules and current authorized workflow state**, not an LLM, experiment or cross-company feed. Suggest one–three next actions, each with Arabic/English reason and dismiss control. A suggestion leads to a reviewable screen; it never posts, pays, submits tax, emails or deletes. Honor roles, fiscal locks, job readiness and A2 scopes again on the actual command. Reject content from imported invoices as instructions.

| Journey/context           | Suggestion and readable reason                                            | Guard / feedback                                                                                                                       |
| ------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Setup incomplete          | “Complete opening balances because month reports need a starting point.”  | Show only allowed setup action; suppress once complete or dismissed.                                                                   |
| Validated draft ready     | “Review these drafts because the required fields and totals match.”       | Link to inbox; no approval when exceptions, missing currency or stale evidence exist.                                                  |
| Open customer invoice     | “Record the received payment because this invoice has an unpaid balance.” | No assumption that money arrived; person supplies evidence/amount and confirms.                                                        |
| Statement unmatched       | “Review this match because amount, reference and date agree.”             | Show competing candidates and score components; still require confirmation; money stays Decimal.                                       |
| Repeated supplier/account | “This account was used on your reviewed bills from this supplier.”        | Minimum three reviewed examples as initial proposed threshold; show uncertainty, allow correction; never share another org's accounts. |
